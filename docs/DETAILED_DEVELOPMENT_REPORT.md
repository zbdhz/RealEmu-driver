# RealEmu-driver 详细开发安排报告（LOCAL 单机场景）

## 1. 文档目的
本报告将当前实现与目标设计之间的差距转化为可执行开发计划，目标是尽快打通并稳定以下闭环：

- 数据面：hwsim -> realwmediumd -> realemu-hw -> FPGA/XDMA -> realwmediumd -> hwsim
- 控制面：mininet-wifi(wserver) -> realwmediumd_dynamic -> realemu-hw

本阶段以 LOCAL 单机模式为准，不引入 REMOTE 扩展逻辑。

---

## 2. 当前状态结论（基线）

### 2.1 已实现能力
- realwmediumd 主循环、netlink 注册、timerfd、wserver 启动流程可运行。
- realemu-hw 已具备：
  - TX/RX 队列管理
  - RX 轮询线程
  - eventfd 通知上层
  - 数据/配置帧打包函数
- realwmediumd 已能把 hwsim 帧转成 MacEvent 入 realemu-hw。
- realwmediumd 已能接收 realemu-hw 的 RX 事件并回送部分 netlink 消息。

### 2.2 关键缺口
- TX 队列到 H2C 的持续出队路径未在 realwmediumd 正常运行路径中稳定执行。
- 缺少“硬件回执(cookie) -> 发送队列元素”精确匹配与提前清理机制。
- 多播包仍进入硬件发送路径，不符合当前“多播软件处理”的简化策略。
- 当前超时逻辑不是固定 100ms（暂定目标），而是沿用原时延模型。
- 控制面参数更新尚未完整同步到硬件（拓扑关键字段）。
- dynamic 删除路径存在返回值逻辑缺陷，可能导致控制面误判。

---

## 3. 总体开发策略

### 3.1 原则
- 对外接口行为尽量保持与 wmediumd 一致。
- 内部先保证“正确性闭环”，再做性能优化。
- 优先完成 P0（必须完成才能称为打通），再做 P1（增强稳定性与一致性）。
- 每个任务必须附带可执行验收标准与回归测试。

### 3.2 里程碑划分
- M0：建立可重复验证基线（编译、运行、日志、最小流量验证）
- M1：完成 P0 数据面闭环
- M2：完成 P1 控制面硬件同步与缺陷修复
- M3：文档与测试收口

---

## 4. 详细开发安排

## 4.1 阶段 M0：基线固化（预计 0.5 天）

### 任务 M0-1：基线构建脚本与运行脚本
- 目标：统一开发环境，避免“能编不能跑/能跑不可复现”。
- 工作项：
  - 固化编译命令（realwmediumd 入口编译）。
  - 固化最小运行命令（含必要 sudo 场景说明）。
  - 增加关键日志开关说明（LOG_DEBUG 级别建议）。
- 产出：
  - 基线运行说明（命令清单）
  - 关键日志检查点列表
- 验收标准：
  - 新环境可按文档独立完成编译与启动。

### 任务 M0-2：基线观测点
- 目标：后续每个任务都能验证“是否真的生效”。
- 工作项：
  - 统计发送入队数、硬件下发数、硬件回包数、超时清理数。
  - 在日志中输出 cookie、src/dst node id、frame type。
- 验收标准：
  - 能通过日志对齐单帧生命周期（入队 -> 下发/回包/超时 -> 回传）。

---

## 4.2 阶段 M1：P0 数据面闭环（预计 2~3 天）

### 任务 P0-1：打通 TX 队列持续下发（最高优先级）
- 目标：realemu_send_pkt_data 入队后，能够持续写入 H2C，而非停留在软件队列。
- 推荐方案：
  - 在 realemu-hw 内新增独立 TX flush 线程（与 RX 轮询线程解耦）。
  - 线程循环调用 realemu_handle_tx_queue，并在空队列时短暂 sleep（如 0.5~1ms）。
- 备选方案：
  - 在 realwmediumd 主循环中增加周期性触发 realemu_handle_tx_queue（不推荐长期使用）。
- 修改范围（建议）：
  - realemu-hw/realemu_hw.h
  - realemu-hw/realemu_hw.c
  - realwmediumd/realwmediumd.c（仅初始化/清理衔接）
- 验收标准：
  - 入队计数与 H2C 写入计数随流量同步增长。
  - 不出现队列长期堆积（稳态下 count 不持续增长）。

### 任务 P0-2：建立 cookie 映射与回执驱动清理
- 目标：由硬件回执驱动队列元素完成态，而不是仅依赖定时器过期。
- 核心设计：
  - 新增 pending_tx 结构（至少包含 cookie、sender、dst、enqueue_time、deadline、ack_state）。
  - 发送入队时写入 pending 索引（hash/list 任一，先求稳可用链表 + 锁）。
  - realemu_rx_event_callback 收到回包后：
    - 按 cookie 命中 pending 项
    - 发送接收通知（HWSIM_CMD_FRAME）
    - 发送发送状态通知（HWSIM_CMD_TX_INFO_FRAME，ACK）
    - 清理 pending 和发送队列关联对象
- 验收标准：
  - 单播成功链路中，同一 cookie 只完成一次成功终态。
  - 不出现“先成功又超时失败”的双终态。

### 任务 P0-3：多播路径回退为纯软件处理
- 目标：符合当前硬件仅支持单播的阶段性约束。
- 实施要点：
  - 在 queue_frame 前置判断：多播/广播包不走 send_frame_to_hardware。
  - 多播沿用软件 deliver 逻辑，并独立超时策略。
- 验收标准：
  - 多播流量日志中不出现硬件下发记录。
  - 多播仍能向目标站点分发并完成 tx_info 回报。

### 任务 P0-4：引入固定 100ms 超时策略（简化版）
- 目标：先满足阶段目标，后续再恢复精细模型。
- 实施要点：
  - 对单播 pending 项直接设置 deadline = enqueue_time + 100ms。
  - 超时触发后输出失败 TX_INFO，并清理 pending。
  - 与成功回执互斥（状态机：PENDING -> SUCCESS/FAILED_TIMEOUT）。
- 验收标准：
  - 硬件无回执时，100ms 左右触发失败（允许调度误差）。
  - 超时失败不再产生接收通知，只产生发送失败状态通知。

---

## 4.3 阶段 M2：P1 控制面同步与缺陷修复（预计 1~2 天）

### 任务 P1-1：补齐 dynamic -> hardware 同步接口
- 目标：让控制面配置不只停留在软件矩阵。
- 建议接口：
  - sync_topology_to_hardware(...)
  - sync_per_to_hardware(...)
  - （可选）sync_station_to_hardware(...)
- 实施要点：
  - 在 realwmediumd_dynamic.h/.c 增加接口与实现。
  - 在 wserver 更新处理函数中接入调用（先拓扑关键字段）。
  - 调用 realemu_send_topo_data / realemu_send_per_data。
- 验收标准：
  - 收到控制面更新后，硬件配置队列计数可观测增加。
  - 同步失败时有明确错误码和日志。

### 任务 P1-2：修复 dynamic 删除返回值逻辑
- 问题：删除成功后仍可能返回 -ENODEV。
- 目标：保证上层控制面收到正确结果。
- 验收标准：
  - 删除存在站点返回成功。
  - 删除不存在站点返回 NOTFOUND。

### 任务 P1-3：统一线程模型描述与代码注释
- 目标：消除“文档是双 RX 线程，代码是 eventfd 回调”这种认知分叉。
- 实施要点：
  - 明确线程分工：
    - 主线程（event loop + timer）
    - RX 轮询线程（realemu-hw）
    - TX flush 线程（新增）
    - wserver 线程
- 验收标准：
  - README 与代码一致，无虚假接口说明。

---

## 4.4 阶段 M3：测试与收口（预计 1 天）

### 任务 T-1：功能测试矩阵
- 单播成功：应回收队列并产生 RX + TX_SUCCESS。
- 单播失败（无回执）：100ms 超时后 TX_FAIL。
- 多播：软件路径完成分发，不经过硬件。
- 控制面拓扑更新：软件矩阵更新 + 硬件同步。

### 任务 T-2：稳定性与并发测试
- 高频流量压测下检查：
  - 队列不会无界增长
  - 无明显死锁
  - 无重复终态

### 任务 T-3：回归测试
- 保证原有 wserver 动态增删站点、SNR/ERRPROB 更新行为不回退。

## 6. 风险与应对

### 风险 R1：并发竞争导致重复回收或悬挂指针
- 应对：
  - pending 状态机原子化（至少加锁保护）
  - 明确唯一终态写入点

### 风险 R2：硬件回包字段不足（例如 cookie 不完整）
- 应对：
  - 在桥接结构中优先保留 cookie 全字段
  - 若短期无法补齐，临时使用 sender+dst+seq 复合键兜底

### 风险 R3：控制面同步失败影响业务可用性
- 应对：
  - 软硬件状态解耦：硬件同步失败不阻塞软件矩阵更新
  - 上报告警并支持重试

## 7. 交付清单（Definition of Done）
- 数据面闭环完成：单播成功/失败路径可稳定复现。
- 多播走软件路径，不走硬件。
- 100ms 超时策略生效并可观测。
- 控制面关键拓扑数据可同步到硬件。
- dynamic 删除返回值问题修复。
- README 与实现一致，无失效接口声明。
- 至少一轮完整回归测试通过并留有测试记录。
